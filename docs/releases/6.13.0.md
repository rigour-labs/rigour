# Rigour 6.13.0

Rigour works while your agent writes. In Claude Code, its hooks now scan every tool call for credentials (they scanned
nothing since 5.1.2), brief the agent with your team's rules before it writes, and hand it a work order that matches what
will stop it. A finding blocks only when Rigour can show it is real, and every check that stopped blocking has a key to make
it block again.

**After upgrading, run `rigour setup`.** Your agent's hooks and its MCP server pin the Rigour version they run, so the fixes
below reach your agent only when setup moves the pins. `rigour doctor` tells you when they are behind.

## While your agent writes (Claude Code)

- **Credentials are scanned before every tool call again, and a real secret is never written.** Since 5.1.2 a Claude Code
  hook payload was mistaken for Cursor's, so the scan before a tool call checked nothing. Now a credential in a real secret's
  format (a provider's key format, a private key, a GCP service account) denies the tool call, and Claude Code shows the agent
  why. One the scan only suspects (a database URL with a password, a JWT) is a warning the agent sees. A found secret is
  never repeated in Rigour's output.
- **`rigour setup` briefs the agent.** From the session's first prompt, and on the first edit of each file, the agent is told
  your repository's rules and your team's lessons for that code. The first-edit briefing never ran in Claude Code before
  (the same payload mistake). `rigour setup --no-brief` leaves it out; re-running setup no longer adds a second briefing
  hook, and `rigour uninstall` removes it.
- **`rigour setup` gives the agent Rigour's tools in every repository**, including one that already had `rigour.yml`, from
  the same release as its hooks: the MCP server is pinned to the CLI's exact version instead of its major. An entry you
  changed yourself is left alone. On Windows, a personal install now finds the `claude` CLI (it reported "no CLI" and
  never registered the server).
- **The agent's work order matches what holds it.** `rigour_get_fix_packet` and `rigour_check` judge the agent's change by
  the stop hook's rule: what must be fixed first, then optional notes, each at its exact line, and nothing from code the
  change did not touch. `rigour_check` with `scope: "repo"` still audits the whole repository. Each security finding gets
  its own fix: a hard-coded key is told to move to the environment and be rotated, not to "parameterize" its query.
- **`rigour doctor` says when your agent runs an older Rigour:** the version the hooks and the MCP server pin, and the one
  installed.
- **Rigour's hooks run in any shell.** Every hook is now a plain command that checks for itself whether Rigour is on in the
  repository, so it runs under Git Bash, PowerShell or cmd. Claude Code on Windows runs hooks in PowerShell when Git Bash is
  not installed: there, a personal install's hooks and a team install's push gate were `sh -c` wrappers and did nothing.
  The cost: each Bash tool call now starts Rigour briefly (a few hundred milliseconds) to see whether it is a push.

## Upgrading: what stopped blocking, and how to keep it blocking

A finding now says how sure its rule is (`certainty`: proven, likely or possible), and only a proven finding blocks. Each check
below used to block and now shows a note by default. Set its key to get the old behaviour back; the key makes the finding
proven, so it blocks.

| Check | Before | Now, by default | To keep it blocking |
|---|---|---|---|
| `security-patterns` | Every pattern blocked: string-built SQL, `innerHTML`, `eval`, weak randomness, a secret-named literal | Only a credential in a format only a real secret has blocks: an AWS access key, a Stripe live key (both new), an `sk-`/`ghp_`-style key, a private key block. Every other pattern is a note, since it cannot see whether its input is trusted | `gates.security.block: true` |
| `ast-analysis`, prototype pollution | A write through `__proto__`, `constructor` or `prototype` blocked | A write is a likely note; a read or an `Object.assign({}, …)` copy a possible one | `gates.security.block: true` |
| `frontend-secret-exposure` | A secret-named variable referenced in client code blocked | A note: bundlers inline only public-prefixed variables, so a non-public one is undefined in the browser. A literal secret key in client code still blocks | `gates.security.block: true` |
| `deprecated-apis`, security category | An API deprecated for security reasons (md5, `eval`, `shell=True`, `new Buffer`) was critical and blocked | A note, shown as high: deprecated is not always vulnerable (md5 for a cache key, `shell=True` with a constant). Python and Go test files are no longer scanned | `gates.deprecated_apis.block_security_deprecated: true` |
| `side-effect-analysis` | An I/O loop with no exit, a self-triggering watcher or a restart without a limit blocked | A note: servers, consumers and daemons do the first by design | `gates.side_effect_analysis.block: true` |
| `offset-paging`, `unbounded-window` | Blocked | Notes: a small or caller-bounded table is fine | `gates.query_patterns.block: true` |
| `duplicate-function` | Blocked | A note: generated code and deliberate per-module copies exist | `gates.duplicate_functions.block: true` |
| `partial-fix`, `partial-wiring` | Blocked | Notes: the difference may be deliberate | `gates.change_sweep.block: true` |
| `diff-tests` | A behaviour change found by diff tests blocked | A note, since an intended change changes behaviour too | Declare an invariant in the pull request's description: a change that breaks it blocks |

The healthcare, fintech, government and devsecops presets set `gates.security.block: true`, so a repository set up from one
of them today keeps those blocks. A `rigour.yml` written from one of them by an earlier version does not have the key; see
the next section.

**Documented example keys never block.** AWS's documented example access key (`AKIA…EXAMPLE`) and Stripe placeholder live
keys (`sk_live_` or `rk_live_` followed only by `x` or `0`, or containing `your`) are not reported. Each exclusion applies only
to its own key shape, so a real token that happens to contain "your" still blocks.

## Upgrading from an older setup

Run `rigour doctor`. It names what an earlier version may have left behind; `rigour setup` fixes all but the last:

- **Hooks or an MCP server on an older Rigour.** Each pins a version, so an upgrade reaches your agent only when setup moves
  the pins. Doctor names the pinned and the installed version; an MCP entry on a floating major (`@rigour-labs/mcp@6`) too.
- **Hooks in a shell wrapper.** A personal install's guard and the push gate were `sh -c` wrappers, which PowerShell cannot
  run. Setup replaces them in place with plain commands.

- **An edit hook that checks nothing.** Older `rigour hooks init` wrote `rigour hooks check --files "$TOOL_INPUT_file_path"`;
  the agent never sets that variable, so no edit was checked. The hook now says so on every edit and exits 1, which the agent
  shows you without stopping the edit. `rigour setup` rewrites Rigour's own hook entries, in the project or, for a personal
  install, at user level, and keeps your other settings.
- **A preset file whose security findings stopped blocking.** A `rigour.yml` made from the healthcare, fintech, government or
  devsecops preset before `gates.security.block` existed. `rigour setup` adds `block: true` under `gates.security`, keeping the
  file's comments and order. A file that sets `block` either way is left alone.
- **`block_security_deprecated: true` written for everyone.** Older `rigour init` wrote it into every `rigour.yml`, so a
  security-deprecated API still blocks there. Keep it if your team chose it; otherwise delete the line. Rigour never changes it.

## The model reviewer (optional)

- **Two opt-in passes: coverage and review points.** With `review.coverage: true`, the judge accounts for every changed
  unit (a finding, or what it checked and why it holds; a unit it skips is shown as not reviewed). With
  `review.review_points: true`, it also names what a careful reviewer would ask to change though nothing breaks, never
  blocking, at most five. Both are off by default: measured, they made each review cost 1.4 to 2.5 times more and found
  nothing the reviewer missed without them.
- **It reviews the diff first.** The general review is now the second step, after earlier human points. The read-trace and
  journey passes are asked for only when the change touches data. A change with no reads or writes is no longer walked
  through checks that cannot apply.
- **The API judge asks a Claude model to cache the conversation**, so each turn can read the earlier ones from the cache.
  Other models cache on their own. The reviewer's tokens now show how many were read from the cache (`--json`
  `reviewer.tokens.cacheRead`, and on its spend line).

## What is shown

- **A note never shows as critical, and most show at most medium.** In a review, a finding that does not block is shown at most high when it is a security
  finding and at most medium otherwise, in `--json` and in the CI summary. A blocking finding keeps its own severity.
- **A score below 100 says what it counts.** Every finding in the files checked costs points, notes included (critical 20,
  high 10, medium 5, low 2, capped per check). A review can pass at 62/100, because only the findings to fix decide the
  verdict. The score itself is unchanged, so score histories stay comparable.
- **With `--notes`, each note is listed under its own line.** Nothing is listed under a "Not shown" line any more, so a note
  is never read as the issue that line left out.

## Learning from reviews

- **`rigour learn-reviews` skips review points that ask for nothing:** a review tool's status lines, a review body's
  summary of what the change does, praise and thanks, and status reports. The summary counts them by reason ("N skipped:
  not a request (describes the change 4, review tool status 3)"). A point with any sign of a request is kept, and a person's
  inline comment is never skipped for describing the code: on a line, that shape states a defect.
- **Measured on public repositories** (the learning-quality report): on logto, precision went from 70% to 98% on the pull
  requests the rules were written against, and from 23% to 44% on later pull requests no rule was written against, with no
  request lost in either. The labels were made in one pass by an AI session. The main set was
  spot-checked by the AI reviewer session (30 sources and 15 body units; recorded in the learning-quality report's README); the held-out set was not
  spot-checked.
- **A review body is read by its structure.** The list under a "Changes", "What changed" or "Summary" heading describes
  the change whatever verbs it uses, and a review tool's own help block ("About…") is its status: neither becomes a
  candidate. In a person's review, a summary bullet is skipped only if it also reads as a description, so a defect stated
  plainly under "## Summary" is kept. On logto's later pull requests (read to find these shapes, so no longer held out),
  precision went from 44% to 100%, with no request lost.
- **`--since` and `--until` learn only what was there then.** Comments and reviews posted on a merged pull request after
  `--until` are no longer learned, and a comment edited after it is kept and marked. Both are compared as times, so an
  offset (`+05:30`) or a bare date works, and a value that is not a time is refused.
- **A lesson verifies by recurrence only from people:** two reviewers, or one reviewer on three or more pull requests at
  least seven days apart. Review bots never count, so a person's point plus a bot's no longer verifies. A lesson an earlier
  version verified by the looser rule goes back to a candidate, saying which rule it missed (`rigour learn-reviews --list`,
  Studio); one a person promoted, corrected, scoped, re-worded or compiled stays verified. Nothing is deleted.
- **The brief serves each rule of a rules file whole.** A numbered list in AGENTS.md or CLAUDE.md was one item cut at 600
  characters; now each item is its own rule, a sentence introducing a list joins its items when they are too short to be
  rules ("must call one of these: `withLock()`; `withLease()`"), and a lead-in that asks nothing is not served. A rule over
  400 characters is served as its first sentence and its line; a briefing stops at 3,000 characters. zulip's AGENTS.md now
  reads as 102 rules instead of 87, none cut.

## Fixed

- **A violation added further down a file is reviewed.** Checks that list a file's violations as one finding are in the
  change when any of them is on a changed line, placed on that line, not only when the first one is.
- **An unguarded parse in a test file is no longer reported.** With `check_unsafe_parse` on, test files in any language are
  skipped by that check: there, an uncaught parse error is the test failing.
- **On Windows, the local model was re-downloaded on every run.** The file's write time could land a few milliseconds after
  the moment Rigour verified it, so a model verified a moment ago looked changed. A difference of up to 2 seconds is now
  allowed; a file changed later than that is still checked again.
- **`rigour learn-reviews` says which account could not read the repository** on a GitHub 401, 403 or 404, naming the
  repository and the account or variable it read as, never the token.
- **A later fix on a bot's candidate never shows it as a person's.** Who raised a point comes only from the review points.

## Measured

- On Rigour's own repository, the 14 most recent first-parent commits on next up to `6ec7900` (after every change in
  this release), each reviewed against its parent (`rigour review --base <parent>`): 0 blocks with 6.12.4 and 0 with this
  release, on every commit.
- The model reviewer on DriftBench (6 of 21 heads of the traced run on 6.13.0-rc.4; the run's budget stopped the rest):
  0 false blocks; with coverage and review points on, 1.4 to 2.5 times the cost per head of 6.12.1 and no recall gain on
  the 9 comparable human points (none better, one worse), which is why both are now opt-in. Whether the API judge's cache
  was read is not measured: the run's tokens did not yet separate it.
