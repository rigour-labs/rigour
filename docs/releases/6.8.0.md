# Rigour 6.8.0

Everything since 6.7.0, in one place. Several of the 6.7.x releases added capability under a `fix:` title, so a patch
number hid them; they are listed here as what they are. From 6.8.0 on, new capability is released as a minor version.

**The idea of this release:** whichever agent your engineers use, its work should arrive already shaped by how your team
builds software. 6.8.0 adds the two pieces that make that a loop rather than a gate: the briefing, before the agent
writes, and the task thread, which holds one piece of work together across agents, checks and reviews.

## Breaking

- **Node 22.13 or later** (since 6.7.2). Rigour uses Node's own SQLite instead of the `sqlite3` package, so it installs
  with no native build. On an older Node, `npm install` refuses with an engines error.

## New in 6.8.0

**The briefing** (off by default). Before an agent writes, it is told what the team asks: the repository's rules that
name the task's files or identifiers, the team's lessons for those files, and the points the team settled against, each
cited. Two moments: before each file's first edit in a session (at most 3 items for that file), and from the session's
first prompt (at most 10 for the task). Claude Code: `rigour hooks init --brief`; with the credential scan on, the
file briefing runs in the scan's own hook (+22 ms per edit, +121 ms on a file's first edit, measured on Rigour's own
repository). Any MCP agent: `rigour_brief`. Anyone: `rigour brief`. Kill switch: `brief.enabled: false` or
`RIGOUR_BRIEF=0`. See [The briefing](../BRIEF.md).

**The task thread.** One piece of work is one task, keyed by the ticket its branch names (once a commit subject or the
pull request title writes it as a ticket) or by the branch. The edit checks, the stop review, the push gate, every review
(with its record's integrity hash) and every briefing are appended to it, in the repository's git folder, shared by its
worktrees. `rigour thread [ticket | branch | #pr] [--json]`. See [The task thread](../THREAD.md).

**A judge that knows the repository, not the person running it.** The Claude judge loads no CLAUDE.md of its own (not
`~/.claude/CLAUDE.md`, not one above the repository) and no auto-memory, from Claude Code 2.1.285; below that, or with an
unreadable version, the review record says the isolation is unverified. The repository's rules reach every judge the
same way: Rigour reads AGENTS.md, CLAUDE.md, Copilot instructions, Cursor rules, the AGENTS.md and CLAUDE.md files in
folders below the root (each applying to its own folder only), and every file they import with an `@path` line.

**The reviewer respects your reviewers.**
- When a review puts a point under its own "Blocking", "Should fix" or "Nits" heading, that label wins over the judge's
  reading, and a disagreement is said on the item. The review record counts how many points took a label.
- A point a reviewer gave as a should-fix is shown, never a block.
- A rule break on a reviewer's point's lines, in like words, is that point found again: one item, not two; a different
  rule there stays its own item.

**`rigour backtest --last N`** lists the last N merged pull requests by merge date, provably, and warns when old pull
requests touched after merge could have crowded recent ones out.

## New in 6.7.x (released as patches)

- **A reviewer panel** (6.7.0): one judge, or two or three from different vendors that agree by evidence; only what most
  confirm blocks.
- **The reviewer as a harness that learns the team, on evidence** (6.7.4): lessons promoted only by outcomes, corrections,
  decisions or recurrence across authors; anti-lessons the judges are told are settled.
- **The repository's rules verified per change, what is shown, and the record of each review** (6.7.6): every rule the
  change touches answered (followed, broken, not applicable, with the code quoted); blocks in full, at most five verified
  should-fixes, the rest folded; a record per review with an integrity hash.
- **Any model as a judge through an API** (6.7.7): any OpenAI-compatible chat-completions API with tools, under the same
  prompt, contract and record. From 6.7.9 its inputs are fed to it, and a judge that gives nothing is asked again or
  replaced by another installed judge.
- **Lessons that are not lessons** (6.7.5): a review bot repeating itself is not recurrence, and a bare file path is not
  a lesson. **A lesson from another pull request reaches the judge** however many lessons the pull request has of its
  own (6.7.8).
- **`rigour backtest --last N`** (6.7.7): the front door to measuring the reviewer on your own history.
- **A reviewer's approval settles the points they raised, a missing thing is searched for across the repository, and a
  block must sit on a line the change touched** (6.7.10): an approval with or without words closes the reviewer's
  earlier points; a real problem in old code near a change is a note, not a block.
- **A key meant for something else never reaches a judge** (6.7.3); **`review --json` says what it checked** (6.7.2);
  releases that npm is slow to serve finish instead of failing half done (6.7.1).

## Upgrade

1. Node 22.13 or later: `node --version`.
2. `npm install -g @rigour-labs/cli@latest` (or `brew upgrade rigour`).
3. Nothing to migrate. Your `rigour.yml`, lessons (`.rigour/review-lessons.json`), review ledger and verdicts are read
   as they are; the new `brief` settings default in. To brief Claude Code, run `rigour hooks init --brief` (or
   `rigour setup` again with the briefing on).

## Known limits

- **Codex and Cursor judges read the person's own config** (`~/.codex/config.toml`, `~/.codex/AGENTS.md`, Cursor's user
  rules): neither has a switch that skips it and keeps the login. The review record names what else they read.
- **Vendored folders** (`vendor/`, `third_party/`, `node_modules/`, ...) are skipped when reading nested rules files;
  the `ignore` list in `rigour.yml` is not used for that yet.
- **A version written in upper case like a ticket** in a commit subject (`UTF-8`) is read as that branch's ticket.
  Naming your project keys in configuration is not built yet.
- **The briefing is as good as your team's recorded knowledge.** On day one it carries mainly your written rules; lessons
  join as reviews give them evidence. Whether a briefing reduces review rounds is not yet measured on live use.

## Rollback

Every package is published under a version and promoted to `latest` only once all of them install. To go back,
point `latest` at 6.7.10 again, package by package:

```bash
node scripts/promote-release.mjs 6.7.10 latest
```

or install it directly: `npm install -g @rigour-labs/cli@6.7.10`. Nothing 6.8.0 writes stops 6.7.10 from running: the
thread and briefing files live in `.git/rigour/` and are ignored by older versions.
